Multi-hub sync — locked design (not yet implemented)

The operator picked Option C on 2026-05-10: application-level event-log sync, active-active. See docs/RFC-004-multi-hub-sync.md §10b for the full design. Quick summary of how the sync will work when it ships:

  • Each hub gets a per-instance append-only outbox_events table that mirrors our existing audit pattern.
  • A replicator daemon polls peers' /api/v1/sync/since?seq=<n> over HTTPS, using the coordinator HMAC bearer pattern for auth.
  • Receiver-side apply is idempotent on UUID-keyed rows; conflicts use last-write-wins on event.at and the audit log retains both versions.
  • Deletes ship as tombstones in outbox_events; receivers write a tombstones row and refuse to recreate the UUID.
  • Steady-state latency target: 1–3 s. Peers are symmetric — no failover procedure.

What will appear on this tab once sync ships

  • Peer status — name, URL, last contact, drift seconds.
  • Replication health — outbox depth, last successful pull, lag windows.
  • Operator actions — probe a peer, pause sync, force a reconciliation (super-admin only).
  • Conflict log — last N LWW resolutions with both pre-images preserved.

Implementation lands after the B1 RBAC slice (RFC-003) ships, because outbox events must carry the new site_id/group_id/device_id scope claims for receiver-side enforcement. Cross-tracked in docs/BACKLOG.md entries B1, B11, B15.
