Single-hub deployment

www.voipguru.org/rebooter and www2.voipguru.org/rebooter both serve from this one backend. There's nothing to sync today, because there's only one logical hub.

The www2 URL nginx-proxies cross-host into this same container. So the "multi-URL fallback" the firmware uses gives you nginx-level resilience (if one nginx is down the other carries traffic) but not a true second hub. Both URLs share fate at the application layer.

What "real sync" would mean

Each URL gets its own backend + Postgres, and the two cross- sync. Audit, devices, deployments, and settings replicate between them. If tmrwww01 dies, devices that know the secondary URL keep working against tmrwww02.

Designed in docs/RFC-004-multi-hub-sync.md. Recommendation: Postgres logical replication (active-passive) for v1, with a clean migration path to active-active later. Awaiting operator redline before implementation.

What ships when the operator picks an option

  • Hub role configurable via REBOOTER_HUB_ROLE env var (primary / secondary / single).
  • Live status on this page: peer reachability, last- successful-sync time, replication lag, forward-queue depth (secondary), last conflict (if any).
  • Operator actions: probe peer, promote-to-primary (super-admin only), enable/disable sync.
  • Failover runbook at docs/runbooks/multi-hub-failover.md.
